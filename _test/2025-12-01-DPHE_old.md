Unlike exact homomorphic encryption schemes, formally defining security notions for the server is challenging in CKKS-based protocols due to the approximate nature of CKKS. We address this by introducing a new security notion called Differentially Private Homomorphic Encryption, which is motivated by differential privacy. Based on this notion, we construct a general compiler that transforms CKKS-based protocols into DPHE protocols. We also present the first zero-knowledge argument of knowledge for CKKS ciphertexts to protect server privacy against malicious clients.*

## 1.Introduction
<div style="margin-top: 1.5em;"></div>

In recent years, CKKS has become a popular choice for building privacy-preserving machine learning (PPML) protocols. 
The primary reason for its popularity is its support for efficient real and complex arithmetic. 
This feature enables straightforward design of machine learning as a service (MLaaS) protocols that protect user privacy. However, in most CKKS-based protocols, server privacy is not guaranteed. Specifically, a client may learn more than just the inference result, potentially gaining access to sensitive information such as model weights or training data. In delegated computation scenarios where the server's model is public, such as in open-source large language models, this is not a major concern. However, in settings where the service provider aims to keep its model private—due to high training costs, risks of model jailbreaking, or legal and regulatory issues involving sensitive data such as health or legal information—protecting server privacy becomes critical. Thus, in this paper, we aim to address the following question in CKKS-based protocols.

>How can we protect the server's privacy in CKKS-based protocols?

### The Peculiarity of CKKS
For other homomorphic encryption (HE) schemes, protecting server privacy has been studied in the context of standard two-party computation (2PC) protocol security. However, this framework cannot be directly applied to CKKS-based protocols due to the scheme’s peculiar properties. The primary reason for this incompatibility lies in the approximate nature of CKKS. Specifically, when encrypting a plaintext $m$, a small noise term $e$ is introduced, resulting in a ciphertext $ct = (a, b)$ of the following structure.
$$
b = as + m + e \pmod{q}
$$
Then, the ciphertext $ct$ is decrypted to $b - as = m + e$, which is only approximately equal to the original plaintext $m$. Due to this peculiarity, prior approaches for achieving 2PC security in HE-based protocols are not adapted to CKKS-based protocols, as they are based on exact HE schemes, which always deliver exact output.

## 2. Server Privacy in Homomorphic Evaluation Protocols  
<div style="margin-top: 1.5em;"></div>

### Estimating Privacy Leakage from Server
In plain MLaaS protocols, server's privacy leakage is usually measured through the lens of differential privacy. In particular, it can be formalized through the notion of differentially private prediction[^1], which is described as follows.

**Definition (DP Prediction).** Let $M : \Theta \times \mathcal{X} \rightarrow \mathcal{Y}$ be a random algorithm. We say that $M$ is an $\epsilon$-differentially private (DP) prediction algorithm if, for every $x \in \mathcal{X}$, the output $M(\theta, x)$ is $\epsilon$-differentially private with respect to $\theta \in \Theta$. In other words, for all adjacent $\theta, \theta' \in \Theta$ and all PPT algorithms $\mathcal{A}$, the following holds. 

$$\Pr[ \mathcal{A}( M(\theta, x) ) = 1] \lesssim e^{\epsilon} \cdot \Pr[\mathcal{A}( M(\theta', x) ) = 1]$$

The above definition models an MLaaS protocol where the client's query is $x$ and the server's model weight or training data is $\theta$. Then, the above definition essentially says that server privacy is maintained regardless of the client's query. Based on the definition of DP-prediction, we model the ideal functionality of the homomorphic evaluation protocol as evaluating some DP-prediction algorithm $M$, which can be described as follows.

**Functionality (Homomorphic Evaluation).** The ideal functionality $F$ for homomorphic evaluation protocol is defined as follows:
- *Client's input*: $x \in \mathcal{X}$  
- *Server's input*: $\theta \in \Theta$  
- *Client's output*: $M(\theta, x)$  
- *Server's output*: $\bot$

Finally, we define the server's privacy in homomorphic evaluation protocol as follows.

**Definition (Server Privacy).** Let $\Pi$ be a homomorphic evaluation protocol that implements ideal functionality $F$. We say $\Pi$ achieves server privacy with parameter $\epsilon$ if $\Pi$ is an $\epsilon$-DP prediction. In other words, the following holds for all PPT adversaries $\mathcal{A}$ that manipulate the client, and all PPT environments $\mathcal{Z}$.  

$$ \Pr[Exec[\Pi_{\theta}, \mathcal{A}, \mathcal{Z}] = 1] \lesssim e^{\epsilon} \cdot \Pr[Exec[\Pi_{\theta'}, \mathcal{A}, \mathcal{Z}] = 1] $$

Then, the above definition ensures that the protocol $\Pi$ protects the server's input in terms of differential privacy against all adversarial clients.

### Secure Homomrphic Evaluation
Before stating our solution, we briefly review prior approaches for achieving server privacy in the case of exact HE schemes. Those approaches usually aim at achieving standard 2PC security, which can be described as follows.

**Definition (Secure Homomorphic Evaluation).** Let $\Pi$ be a homomorphic evaluation protocol that implements ideal functionality $F$. We say $\Pi$ is a secure homomorphic evaluation protocol for $F$ if there exists a PPT simulator $\mathcal{S}$ such that the following holds for all PPT adversaries $\mathcal{A}$ that manipulate the client, and all PPT environments $\mathcal{Z}$.  

$$ \Pr[Exec[\Pi_{\theta}, \mathcal{A}, \mathcal{Z}] = 1] \approx \Pr[Exec[F_{\theta}, \mathcal{S}, \mathcal{Z}] = 1] $$

The primary reason for achieving the above property is as follows.

**Theorem (Secure Homomorphic Evaluation).** Let $F$ be the ideal functionality for homomorphic evaluation of an $\epsilon$-DP prediction algorithm $M$, and let $\Pi$ be a secure homomorphic evaluation protocol that implements the ideal functionality $F$. Then, $\Pi$ achieves server privacy with parameter $\epsilon$.

Thus, if the ideal functionality $F$ is defined for a DP prediction algorithm and $\Pi$ is a secure homomorphic evaluation protocol, then we can ensure server privacy in the real execution of the protocol $\Pi$.

## 3. Differentially Private Homomrphic Evaluation
<div style="margin-top: 1.5em;"></div>

### Definition
We observe that when applying the previous framework to CKKS-based protocols for achieving server privacy, the main difficulty arises from achieving computational indistinguishability between the ideal functionality and the real protocol execution. However, if server privacy is estimated in terms of differential privacy, requiring computational indistinguishability can be an overkill. Thus, we relax the definition of secure homomorphic evaluation to differentially private homomorphic evaluation[^2] as follows.

**Definition (Differentially Private Homomorphic Evaluation).** Let $\Pi$ be a homomorphic evaluation protocol that implements ideal functionality $F$. We say $\Pi$ is an $\epsilon$-differentially private homomorphic evaluation (DPHE) protocol for $F$ if there exists a PPT simulator $\mathcal{S}$ such that the following holds for all PPT adversaries $\mathcal{A}$ that manipulate the client, and all PPT environments $\mathcal{Z}$.  

$$ \Pr[Exec[\Pi_{\theta}, \mathcal{A}, \mathcal{Z}] = 1] \lesssim e^{\epsilon} \cdot \Pr[Exec[F_{\theta}, \mathcal{S}, \mathcal{Z}] = 1]$$

$$\Pr[Exec[F_{\theta}, \mathcal{S}, \mathcal{Z}] = 1] \lesssim e^{\epsilon} \cdot \Pr[Exec[\Pi_{\theta}, \mathcal{A}, \mathcal{Z}] = 1]
$$

In the above definition, the computational indistinguishability condition is relaxed to something analogous to computational differential privacy[^3]. Once a protocol satisfies the DPHE property, we can derive the following result.

**Theorem (Differentially Private Homomorphic Evaluation).** Let $F$ be the ideal functionality for homomorphic evaluation of an $\epsilon$-DP prediction algorithm $M$, and let $\Pi$ be an $\epsilon'$-DPHE protocol that implements the ideal functionality $F$. Then, $\Pi$ achieves server privacy with parameter $\epsilon + 2\epsilon'$.

Therefore, to ensure server privacy in terms of differential privacy, it suffices to achieve the DPHE property for the homomorphic evaluation protocol $\Pi$, instead of computational indistinguishability.

### Instantiation
Next, we show how to instantiate a DPHE protocol by compiling existing CKKS-based protocols. The core idea is to utilize the Laplace mechanism[^4] to achieve differential privacy. Suppose a protocol $\Pi$ aims at evaluating a DP mechanism $M$ on the client's encrypted input $ct_{in} = Enc(x)$. Let $\tau > 0$ be an $L1$-norm bound for the noise when evaluating $M$ in CKKS evaluation algorithms for $\theta \in \Theta$ and $x \in \mathcal{X}$. Then, the compilation is achieved as follows.


1. $(c_0, c_1) \gets Eval\big( M(\theta, \cdot), ct_{in} \big) \pmod {q}$
2. $(c'_0, c'_1) \gets (c_0, c_1) + (\lceil t \rfloor, 0) \pmod{q}$ for $t \gets Lap(\tau / \epsilon')^N$.
3. $ct_{out} \gets q' \cdot (c_0, c_1) + Enc_{pk}(0) \pmod{qq'}$

The second step is for achieving the differential privacy property on the client's output plaintext, and the third step is to remove any remaining information in the ciphertext components by adding an encryption of zero. As a corollary, our compiler achieves the following result.  

**Corollary (DPHE Compiler).** Let $F$ be the ideal functionality for homomorphic evaluation of an $\epsilon$-DP prediction algorithm $M$. Then, the DPHE compiler produces an $\epsilon'$-DPHE protocol $\Pi$ that implements $F$, and $\Pi$ achieves server privacy with parameter $\epsilon + 2\epsilon'$.

Therefore, by relaxing the security notion for homomorphic evaluation protocols, we succeed in achieving server privacy in CKKS-based protocols.

## 4. ZKAoK for CKKS Ciphertexts
<div style="margin-top: 1.5em;"></div>

Our DPHE compiler is based on the assumption that the input ciphertext is well-formed and the input message lies in the domain $\mathcal{X}$. However, for malicious clients, there is no guarantee that the input ciphertext satisfies these conditions. Thus, for the server to verify these conditions without compromising the client's privacy, we need a zero-knowledge argument of knowledge (ZKAoK) for CKKS ciphertexts.

However, designing ZKAoK for CKKS is nontrivial, and there have been no previous attempts for it. The main difficulty arises from the lack of techniques for verifying the validity of the message, i.e., $x \in \mathcal{X} \subseteq \mathbb{R}^N$. To be precise, when encrypting a message $x \in \mathbb{R}^N$, it is encoded into a polynomial $m(X) \in R_q$ that lies in the ciphertext space $R_q = \mathbb{Z}_q[X]/(X^N + 1)$. Current ZKAoK for HE ciphertexts only support verification of arithmetic relations defined over $R_q$, whereas we need to verify the condition $x \in \mathcal{X}$, which is defined over $\mathbb{R}^N$.

### Solution
We address this issue by delegating the encoding procedure to the server, described as follows.

1. The client generates a ciphertext with scaled coefficient packing. i.e, the plaintext $m$ is generated by $a_0 + a_1 X + \cdots a_{N-1}X^{N-1}$ for $\lceil \Delta x \rfloor := (a_0, \dots, a_{N-1}) \in \mathbb{Z}^N$.
2. The client generates a ZKAoK that proves the coefficient of $m$ lies in the scaled domain $\lceil \Delta \mathcal{X} \rfloor$ through ZKAoK for HE[^5].
3. The server verifies the ZKAoK for the client's ciphertext.
4. The server generates the final input ciphertext by applying coeff-to-slot operations.

The scaled coefficient packing in the first step allows a client to generate a ZKAoK for verifying the input domain. After the server verifies this ZKAoK, it can generate an input ciphertext whose slot values correspond to these coefficient values by applying the coeff-to-slot operation. As a result, the server can ensure that input ciphertexts are well-formed, i.e., the input messages lie within the input domain. With the above technique, we instantiate the first ZKAoK for CKKS ciphertexts that can verify the input domain.
